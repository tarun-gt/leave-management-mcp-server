# Leave Management MCP Server

A Python-based **Model Context Protocol (MCP) server** for managing
employee leave requests using **PostgreSQL**. It exposes
leave-management functionality as MCP tools and resources so an
MCP-compatible client can interact with employee records, leave
balances, leave requests, and leave calendars.

## Features

### MCP tools

  -----------------------------------------------------------------------
  Tool                                Description
  ----------------------------------- -----------------------------------
  `check_leave_balance`               Retrieves an employee's available
                                      balance for each leave type.

  `submit_leave_request`              Submits a leave request, calculates
                                      working days (Monday--Friday), and
                                      stores the request and its
                                      individual leave dates.

  `review_leave_request`              Approves or rejects a pending
                                      request. Approval deducts the
                                      requested days from the employee's
                                      leave balance.

  `get_employee_leave_dates`          Retrieves an employee's leave
                                      dates, with optional status and
                                      month filters.

  `check_date_availability`           Lists employees who have approved
                                      leave on a specified date.

  `list_leave_requests`               Lists leave requests, optionally
                                      filtered by status and employee.
  -----------------------------------------------------------------------

### MCP resources

  -----------------------------------------------------------------------
  Resource URI                        Description
  ----------------------------------- -----------------------------------
  `policy://company/leave`            Returns the company's leave policy.

  `balances://{employee_id}`          Returns leave balances for the
                                      specified employee.
  -----------------------------------------------------------------------

## Setup

### 1. Clone the repository

``` bash
git clone https://github.com/YOUR_USERNAME/leave-management-mcp-server.git
cd leave-management-mcp-server
```

Replace `YOUR_USERNAME` with your GitHub username.

### 2. Install dependencies

``` bash
uv sync
```

The dependencies used by this project can be added with:

``` bash
uv add "mcp[cli]"
uv add "psycopg[binary]"
uv add python-dotenv
```

`uv add` adds a dependency to `pyproject.toml` and updates the lock
file. `uv sync` installs the dependencies declared by the project.

### 3. Create the PostgreSQL database

For example, create a database named `leave_management`:

``` sql
CREATE DATABASE leave_management;
```

Connect to that database before running the table creation statements
below.

### 4. Configure environment variables

Create a `.env` file in the project root:

``` env
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@localhost:5432/leave_management
```

Replace `YOUR_PASSWORD` with your PostgreSQL password.

The application loads this value using `python-dotenv`. Keep `.env`
private and do not commit it to Git.

Create a `.env.example` file for other developers, containing
placeholders only:

``` env
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@localhost:5432/leave_management
```

### 5. Create the database tables

Run the following SQL while connected to the `leave_management`
database.

#### Employees

Stores employee details. `employee_id` is the primary key.

``` sql
CREATE TABLE employees (
    employee_id VARCHAR(20) PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    department VARCHAR(100) NOT NULL
);
```

#### Leave balances

Stores the available number of days for each employee and leave type.
Each employee can have one balance row per leave type.

``` sql
CREATE TABLE leave_balances (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    employee_id VARCHAR(20) NOT NULL,
    leave_type VARCHAR(20) NOT NULL,
    available_days INTEGER NOT NULL DEFAULT 0,

    CONSTRAINT fk_balance_employee
        FOREIGN KEY (employee_id)
        REFERENCES employees(employee_id),

    CONSTRAINT uk_employee_leave
        UNIQUE (employee_id, leave_type),

    CONSTRAINT ck_leave_type
        CHECK (leave_type IN ('VACATION', 'SICK', 'PERSONAL')),

    CONSTRAINT ck_available_days
        CHECK (available_days >= 0)
);
```

#### Leave requests

Stores the overall request, including its date range, number of
requested working days, reason, status, and reviewer remarks.

``` sql
CREATE TABLE leave_requests (
    request_id VARCHAR(20) PRIMARY KEY,
    employee_id VARCHAR(20) NOT NULL,
    leave_type VARCHAR(20) NOT NULL,
    start_date DATE NOT NULL,
    end_date DATE NOT NULL,
    days_requested INTEGER NOT NULL,
    reason VARCHAR(500),
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    remarks VARCHAR(500),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_request_employee
        FOREIGN KEY (employee_id)
        REFERENCES employees(employee_id),

    CONSTRAINT ck_request_leave_type
        CHECK (leave_type IN ('VACATION', 'SICK', 'PERSONAL')),

    CONSTRAINT ck_request_status
        CHECK (status IN ('PENDING', 'APPROVED', 'REJECTED')),

    CONSTRAINT ck_request_dates
        CHECK (end_date >= start_date),

    CONSTRAINT ck_request_days
        CHECK (days_requested > 0)
);
```

#### Individual leave dates

Stores each working date associated with a request. This supports
overlap checks and date-based availability queries. Deleting a request
also deletes its associated date rows.

``` sql
CREATE TABLE leave_request_dates (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    request_id VARCHAR(20) NOT NULL,
    leave_date DATE NOT NULL,

    CONSTRAINT fk_leave_request
        FOREIGN KEY (request_id)
        REFERENCES leave_requests(request_id)
        ON DELETE CASCADE,

    CONSTRAINT uk_request_date
        UNIQUE (request_id, leave_date)
);
```

## Run the MCP server with MCP Inspector

Start the MCP development inspector from the repository root:

``` bash
uv run mcp dev src/my_first_mcp_server/__init__.py
```

The command launches the MCP development environment and MCP Inspector.
Open the Inspector URL printed in the terminal (commonly
`http://127.0.0.1:6274`).

Keep the terminal process running while using Inspector. Stop it with
`Ctrl+C`.

Use Inspector to connect to the server, view its resources and tools,
and invoke the tools with test arguments.

signatures.

### Submit a leave request

``` json
{
  "employee_id": "EMP001",

  "end_date": "2026-11-09",
```

## Leave request lifecycle

1.  An employee submits a request.
2.  The server validates the employee, leave type, date range, balance,
    and overlapping pending or approved leave.
3.  The server inserts the request into `leave_requests` and its working
    dates into `leave_request_dates`.
4.  The request starts with `PENDING` status.
5.  An authorized reviewer approves or rejects the request.
6.  On approval, the server deducts the requested days from
    `leave_balances` and updates the request status.
7.  On rejection, the status changes to `REJECTED`; the balance is not
    deducted.

Pending requests do not deduct or reserve leave balance in the current
business logic. Public holidays are not excluded by the current
Monday--Friday working-day calculation.

## Database relationships

``` text
employees
   │
   ├──< leave_balances
   │
   └──< leave_requests
             │
             └──< leave_request_dates
```

-   One employee can have multiple leave-balance rows, one per leave
    type.
-   One employee can submit multiple leave requests.
-   One leave request can contain multiple individual working dates.
-   `leave_request_dates.request_id` references
    `leave_requests.request_id` with `ON DELETE CASCADE`.

## Troubleshooting

### `DATABASE_URL is missing`

-   Confirm that `.env` exists in the repository root.
-   Confirm that it contains `DATABASE_URL=...`.
-   Verify the database name, username, password, host, and port.
-   Ensure the application loads the root `.env` file.

### PostgreSQL connection error

-   Confirm PostgreSQL is running.
-   Confirm the `leave_management` database exists.
-   Verify the credentials in `DATABASE_URL`.
-   Confirm that the tables were created in the correct database.

### MCP tool execution error

-   Check the terminal running `mcp dev` for the Python traceback.
-   Verify that the MCP tool arguments match the function signatures.
-   Verify that the database contains the expected employee and balance
    records.
-   Check that the request ID and leave type satisfy the database
    constraints.

### `AttributeError: 'Connection' object has no attribute 'executemany'`

With Psycopg 3, call `executemany()` on a cursor, not on the connection:

``` python
with conn.cursor() as cur:
    cur.executemany(
        """
        INSERT INTO leave_request_dates (request_id, leave_date)
        VALUES (%s, %s)
        """,
        rows
    )
```

## Security notes

-   Never commit `.env`, database passwords, API keys, or access tokens.
-   Keep `.env` in `.gitignore`.
-   Use `.env.example` with placeholder values for documentation.
-   Use a restricted PostgreSQL user for application access rather than
    a database superuser.
-   Do not expose raw database exception details to end users in
    production; log diagnostic details securely.
